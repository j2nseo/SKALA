# 판교 1반 P014 박진서
# 2026.08.27

Vue 기본 문법부터 Composition API, 컴포넌트, Vue Router, Pinia, Axios, UI Library, 배포까지 단계별 과제를 하나의 서비스로 발전시킨 날씨 대시보드이다.

처음에는 정해진 도시와 날씨를 카드로 출력하는 작은 화면이었지만 과제를 진행할수록 검색과 상세 화면, 전역 온도 단위, 실제 날씨 API, 5일 예보, 생활 가이드를 추가했다. 각각의 예제를 따로 실행하는 것이 아니라 각 단계의 결과를 다음 단계에서 재사용하면서 실제로 이용할 수 있는 하나의 서비스 형태로 완성하고자 했다.

## 주요 기능

- 서울·수원·부산·제주의 현재 날씨 카드 제공
- 한글과 영문 도시명 실시간 필터링 및 외부 도시 검색
- OpenWeatherMap 현재 날씨와 5일 예보 조회
- Open-Meteo 지오 코딩을 이용한 국내 지명 검색 보완
- 카드 내부 상세 정보와 도시별 상세 페이지 제공
- 섭씨/화씨 전역 단위 전환
- 로딩·빈 결과·API 오류 상태 안내
- 서비스 소개, 날씨별 생활 가이드, 404 페이지 제공
- 모바일 화면에서도 사용할 수 있는 반응형 레이아웃

## 과제 진행 과정

### 1 - Vue 기본 문법으로 날씨 Mockup 만들기

첫 단계에서는 `ref`로 서울·수원·부산 날씨 배열을 만들고 `v-for`와 `:key`로 카드를 반복적으로 렌더링했다. 25도를 기준으로 더움과 선선함 라벨을 나누면서 데이터에서 화면 상태를 계산하는 방법도 적용했다.

검색창은 한글 조합 입력이 자연스럽게 반영되도록 `:value`와 `@input`을 사용했다. 카드 클릭과 상세보기 버튼의 이벤트가 함께 실행되지 않도록 `.stop`을 적용했고 기본 데이터에 제주를 추가해 화면을 직접 확장했다.

**느낀 점**

단순히 배열을 화면에 출력하는 것보다 각 데이터에 고유한 `id`를 두고 상태에 따라 라벨을 결정하니 이후 컴포넌트와 라우터 단계에서 같은 데이터를 훨씬 쉽게 재사용할 수 있었다. 작은 데이터 구조를 결정하는 것이 다음 기능의 난이도에 영향을 준다는 점을 배웠다.

### 2 - Composition API로 상태와 검색 로직 정리하기

`searchQuery`, `selectedCity`, `weatherList`를 반응형 상태로 분리하고 `filteredWeatherList`를 `computed`로 작성했다. 검색어가 비어 있으면 전체 목록을, 입력 중이면 도시명이 포함된 항목만 출력하며 결과가 없을 때는 별도의 안내 문구가 나타난다.

`watch`로 선택 도시 변경을 확인하고 `watchEffect`로 검색어 변화를 추적했다. 이후 API 로딩 상태와 검색 결과 상태도 같은 방식으로 반응형 데이터에 추가했다.

**느낀 점**

템플릿 안에 조건식을 길게 작성하는 것보다 계산된 값과 상태 변경 로직을 스크립트 영역에 모아서 보니 화면 코드가 읽기 쉬워졌다. `computed`는 결과를 만드는 데에 있어서, `watch`는 변화에 따른 부수 작업을 처리하는 데에 있어서 적합하다는 차이도 실제 검색 기능을 만들며 이해할 수 있었다.

### 3 - 화면을 재사용 가능한 컴포넌트로 분리하기

하나의 화면에 있던 기능을 다음 컴포넌트로 분리했다.

| 컴포넌트 | 역할 |
| --- | --- |
| `BaseDashboardCard.vue` | 검색·날씨·예보 영역의 공통 카드 레이아웃과 Slot 제공 |
| `SearchBar.vue` | 검색어 표시, 입력 이벤트와 검색 실행 이벤트 전달 |
| `WeatherCard.vue` | 도시 날씨 표시, 카드 선택과 상세 페이지 이벤트 전달 |
| `UnitToggler.vue` | Pinia의 온도 단위 변경 Action 실행 |
| `ForecastPanel.vue` | 5일 예보 목록과 단위 변환 결과 출력 |

데이터는 Props로 내려보내고 사용자 동작은 Emits로 올려보냈다. 공통 카드에는 기본 Slot을 배치해 같은 디자인 안에 서로 다른 콘텐츠를 넣을 수 있도록 했고 각 컴포넌트의 스타일은 `scoped`로 분리했다.

**느낀 점**

처음에는 파일 수가 늘어나는 것이 오히려 복잡해 보였지만 역할을 작게 나누니 검색창이나 카드 디자인을 수정할 때 어디까지 영향을 미치는지 그 범위가 명확해졌다. Props와 Emits를 기준으로 데이터 흐름을 한 방향으로 유지하는 것이 컴포넌트 구조를 이해하는 데 도움이 됐다.

### 4 - Vue Router로 페이지 구조 만들기

`WeatherHomeView`, `WeatherDetailView`, `WeatherAboutView`, `WeatherGuideView`, `NotFoundView`를 만들고 모든 View를 지연 로딩했다. `/weather/:cityId` 동적 경로로 도시 ID를 전달하며 API에서 검색한 도시는 쿼리의 도시명으로 다시 조회한다. 그리고 정의하지 않은 주소는 Catch-all Route가 404 화면으로 연결한다.

기본 카드 클릭은 현재 화면에서 상세 정보를 빠르게 펼치고 `상세 페이지` 버튼은 이벤트 버블링 없이 동적 상세 경로로 이동하도록 구성했다. 과제에서 요구한 Programmatic Navigation과 기존 카드 상호작용을 함께 유지했다.

**느낀 점**

컴포넌트 전환과 페이지 이동은 비슷해 보이지만 URL을 기준으로 상태를 복원할 수 있다는 점에서 차이가 크게 존재했다. 상세 페이지를 직접 새로고침해도 도시 ID로 데이터를 찾도록 만들면서 라우트 파라미터가 화면 상태의 일부라는 점을 알게 됐다.

### 5 - Pinia로 온도 단위 공유하기

`configStore`에 `unit` 상태, `unitSymbol` Getter, `toggleUnit` Action을 작성했다. 추가 기능으로 마지막 API 갱신 시각을 저장하는 `lastUpdated`, `formattedLastUpdated`, `markUpdated`도 구현했다.

온도 단위는 메인 카드, 메인 배너, 상세 페이지, 5일 예보에 공통으로 반영된다. 어느 화면에서 단위를 바꾸더라도 같은 Store를 참조하기 때문에 전체 서비스가 즉시 함께 변경된다는 것을 확인할 수 있다.

**느낀 점**

여러 컴포넌트에 같은 값을 Props로 계속 전달하는 것보다 전역 설정을 Store로 관리하는 편이 구조에 잘 맞았다. 모든 데이터를 Store에 넣는 것이 아니라 여러 화면이 공유해야 하는 설정만 선택하는 것이 중요하다고 생각했다.

### 6 - Axios와 실제 날씨 API 연결하기

Axios 인스턴스를 용도별로 나눠 OpenWeatherMap의 현재 날씨, 5일 예보, 지오코딩 API를 호출했다. OpenWeatherMap에서 일부 한글 지명을 찾지 못하는 경우를 보완하기 위해 Open-Meteo 지오코딩과 간단한 한글 로마자 변환을 추가했다.

API 키는 코드에 작성하지 않고 `VITE_OPENWEATHER_API_KEY` 환경 변수로 분리했다. 요청 실패 시 기본 Mock Data를 유지하고 상태바에 오류 원인을 표시해 화면 전체가 비어있지 않도록 했다.

**느낀 점**

Mock Data에서는 항상 같은 형태의 데이터가 들어오지만 외부 API는 검색 실패, 네트워크 오류 문제와 언어별로 도시명이 다르다는 점도 고려해야 했다. 실제 데이터를 연결하면서 정상 결과뿐 아니라 실패했을 때의 화면도 기능의 일부라는 점을 느낄 수 있었다.

### 7 - Element Plus와 개인화 UI 적용하기

Element Plus를 전역 등록하고 새로고침 버튼과 온도 단위 버튼에 적용했다. 또 기본 예제 디자인 대신 보라색 사이드바, 대시보드 배너, 카드 확장 애니메이션, 상태별 아이콘과 생활 안내를 추가해 날씨 모니터링 서비스 형태로 개인화했다.

추가 View인 생활 가이드에서는 맑음·비·강풍·추위 상황별 준비 사항을 카드로 제공하고 있고 API 확장 기능으로 서울 5일 예보 패널도 추가했다.

**느낀 점**

UI Library는 화면 전체를 대신 만들어 주는 도구라기보다는 반복되는 버튼 상태와 접근성을 처리하는데에 있어 안정적으로 가져오는 데 유용했다. 라이브러리 컴포넌트와 직접 작성한 CSS의 역할을 나누어보니 원하는 디자인을 유지하면서 더 효율적으로 개발을 진행할 수 있었다.

### 8 - 코드 품질 점검과 Build

ESLint에 엄격한 비교 연산자 규칙을 적용하고 Prettier로 코드 형식을 통일했다. 개발·스테이징·프로덕션 환경을 분리할 수 있도록 Vite mode별 빌드 스크립트를 구성했고 API 키가 포함된 `.env.local`은 Git에서 제외했다.

`npm run lint`와 `npm run build`를 통과한 정적 파일만 배포 대상으로 사용한다.

**느낀 점**

개발 서버에서 정상으로 보이는 것과 배포 가능한 코드는 같지 않았다. 따라서 린트와 프로덕션 빌드를 마지막에 한 번 실행하는 절차를 거치는 것이 문법 오류, 환경 변수 누락, 번들 문제를 찾는 가장 기본적인 안전장치라는 점을 확인할 수 있었다.


## 트러블슈팅

### 1) 한글로 검색한 도시를 API에서 찾지 못하는 문제

처음에는 OpenWeatherMap만 연결하면 한글 도시명도 모두 검색될 것이라 생각했다. 그런데 일부 지역은 한글로 입력했을 때 검색 결과가 나오지 않았고 영문으로 입력을 해야 찾을 수 있었다.

OpenWeatherMap에 등록된 도시명과 입력한 한글 지명이 정확히 일치하지 않는 것이 원인이었다. 이를 해결하기 위해 Open-Meteo 지오코딩을 추가로 연결해 국내 지명을 먼저 좌표로 찾도록 했고 여기에서도 찾지 못하면 한글을 간단히 로마자로 바꿔 다시 검색하도록 처리했다.

### 2) 배포한 화면에서 실제 날씨가 나오지 않는 문제

로컬에서는 실제 날씨가 잘 나왔지만 Vercel에 처음 배포했을 때는 API 키가 없다는 오류가 발생했다. `.env.local`은 Git에 올라가지 않도록 설정했기 때문에 Vercel에는 API 키가 전달되지 않은 상태였기 때문이다.

API 키를 코드나 GitHub에 올리는 대신 Vercel의 Environment Variables에 `VITE_OPENWEATHER_API_KEY`를 따로 등록해서 해결했다. 또, API 요청이 실패하더라도 화면 전체가 비어버리지 않도록 기본 날씨 데이터와 오류 안내도 남겨두었다.

### 3) 상세 페이지 버튼을 눌렀는데 카드도 같이 열리는 문제

날씨 카드 안에 상세 페이지 버튼을 추가했는데 버튼을 누르면 페이지 이동뿐만 아니라 카드의 상세 정보까지 같이 펼쳐지는 문제가 있었다.

버튼의 클릭 이벤트가 상위 카드까지 전달되는 이벤트 버블링 때문이었고 상세 페이지 버튼에 `@click.stop`을 적용해 버튼을 눌렀을 때는 페이지 이동 이벤트만 실행되도록 수정했다.

### 4) 상세 페이지 주소에서 새로고침하면 404가 나오는 문제

메인 화면에서 상세 페이지로 이동할 때는 문제가 없었지만 `/weather/2` 같은 주소에서 바로 새로고침하면 Vercel의 404 화면이 나왔다.

Vue Router는 브라우저에서 경로를 처리하지만 Vercel은 `/weather/2`라는 실제 파일을 찾으려고 해서 생긴 문제였다. `vercel.json`에 Rewrite를 추가해 어떤 경로로 접속하더라도 먼저 `index.html`을 불러오도록 설정했다.

### 5) 검색어를 입력해도 카드 목록이 그대로 보이는 문제

검색창에 입력한 내용과 상태 메시지는 바뀌는데 날씨 카드 목록은 그대로 남아 있었다. 확인해보니 `filteredWeatherList`가 이름과 달리 검색어를 사용하지 않고 원본 배열만 반환하고 있었기 때문이었다.

`computed` 안에서 입력한 검색어의 앞뒤 공백을 제거하고 도시 이름에 검색어가 포함되어 있는지 확인하도록 수정했고 검색어가 없을 때는 전체 목록을 보여주고 일치하는 도시가 없을 때는 검색 결과가 없다는 문구가 나오도록 처리했다.

## 프로젝트 구조

```text
src/
├── assets/                 # 전역 스타일과 이미지
├── components/
│   └── exercise/           # 최종 대시보드 컴포넌트
├── router/                 # 페이지 경로와 동적 라우트
├── services/               # 날씨·지오코딩 API 요청
├── stores/                 # Pinia 전역 설정
├── views/                  # 라우트 단위 화면
├── App.vue                 # 공통 사이드바와 RouterView
└── main.js                 # Vue, Router, Pinia, Element Plus 등록
```

## 실행 방법

### 1. 의존성 설치

```sh
npm install
```

### 2. 환경 변수 설정

`.env.example`을 참고해 프로젝트 루트에 `.env.local`을 만든다.

```env
VITE_OPENWEATHER_API_KEY=발급받은_API_KEY
```

OpenWeatherMap API 키가 없어도 기본 Mock Data 화면은 확인할 수 있지만 실제 날씨 검색과 5일 예보는 사용할 수 없다.

### 3. 개발 서버 실행

```sh
npm run dev
```

### 4. 품질 검사와 프로덕션 빌드

```sh
npm run lint
npm run build
npm run preview
```

## 환경별 빌드

```sh
npm run build:staging
npm run build:production
```

- `.env.staging`: 스테이징 환경 설정
- `.env.production`: 프로덕션 환경 설정
- `.env.local`: 개인 API 키이며 Git에 포함하지 않음

## 배포

- 배포 주소: [https://weatherly-skala.vercel.app](https://weatherly-skala.vercel.app)
- 배포 환경에는 `VITE_OPENWEATHER_API_KEY`를 별도로 등록해야 한다.
- SPA의 동적 경로를 직접 열어도 `index.html`로 연결되도록 Rewrite 설정이 필요하다.

## 과제를 마치며

처음에는 java script에 대한 이해도 부족해서 Vue를 사용하는 것도 어려웠지만 실습을 진행하다보니 어떤 문법이 어떻게 작동하는지 확인하며 학습할 수 있었다. 또 Vue 문법을 확인하기 위한 간단한 날씨 안내 기능이 있는 페이지로 시작했지만 각 단계를 이전 결과 위에 하나씩 쌓으면서 상태 관리, 컴포넌트 통신, 라우팅, 외부 API, 전역 설정, 배포가 서로 연결되는 과정을 경험할 수 있었다.

특히 기능을 하나 추가할 때 화면만 바꾸는 것이 아니라 데이터 구조, 컴포넌트 이벤트, URL, 실패 상태까지 함께 고려하며 구성해야 서비스가 자연스럽게 동작한다는 점을 배웠다. 각 과제가 독립적인 것이 아니라 조금씩 얹어 가면서 학습할 수 있어서 보다 이해하기 쉬웠고 실제로 검색하고 이동하면서 사용할 수 있는 하나의 대시보드로 완성했다는 점이 가장 의미있었다.
