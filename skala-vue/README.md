# Weatherly - Vue 날씨 대시보드

Vue 수업에서 배운 내용을 하나씩 적용하면서 만든 날씨 대시보드입니다.

처음에는 서울, 수원, 부산의 날씨를 카드로 보여주는 간단한 화면이었습니다. 수업 진도에 맞춰 검색 기능과 상세 페이지를 만들고 온도 단위 변경, 실제 날씨 API, 5일 예보 등을 하나씩 추가하면서 지금의 대시보드 형태가 되었습니다.

## 주요 기능

- 서울·수원·부산·제주의 현재 날씨 확인
- 한글과 영문 도시명 필터링 및 도시 검색
- OpenWeatherMap을 이용한 실제 날씨와 5일 예보 조회
- Open-Meteo 지오코딩을 활용한 국내 지명 검색 보완
- 카드 내부 상세 정보와 도시별 상세 페이지
- 섭씨·화씨 단위 변경
- 로딩, 검색 결과 없음, API 오류 상태 안내
- 서비스 소개, 날씨별 생활 가이드, 404 페이지
- 모바일 화면을 고려한 반응형 레이아웃

## 과제 진행 과정

### 1 - Vue 기본 문법으로 날씨 Mockup 만들기

처음에는 `ref`로 서울, 수원, 부산의 날씨 데이터를 만들고 `v-for`와 `:key`를 사용해 카드를 반복해서 출력했습니다. 기온이 25도 이상이면 더움, 25도 미만이면 선선함으로 표시되도록 조건도 나눴습니다.

검색창은 한글 입력이 바로 반영되도록 `:value`와 `@input`을 사용했습니다. 카드와 상세보기 버튼의 클릭 이벤트가 같이 실행되지 않도록 `.stop`도 적용했고, 기본으로 주어진 데이터 외에 제주 날씨를 직접 추가했습니다.

**진행하면서 느낀 점**

처음에는 도시와 날씨들을 화면에 반복해서 보여주는 것이라고만 생각했습니다. 그런데 데이터마다 `id`를 넣고 상태를 구분해두니 컴포넌트나 상세 페이지를 만들 때 그대로 활용할 수 있었고 초반에 데이터 구조를 어떻게 정하는지가 생각보다 중요하다는 걸 느꼈습니다.

### 2 - Composition API로 상태와 검색 기능 정리하기

검색어, 선택한 도시, 날씨 목록을 각각 `searchQuery`, `selectedCity`, `weatherList`로 나눠 관리했습니다. `filteredWeatherList`는 `computed`로 만들어 검색어가 없을 때는 전체 도시를 보여주고, 검색어를 입력하면 일치하는 도시만 남도록 했습니다.

`watch`로 선택한 도시가 바뀌는 것을 확인하고, `watchEffect`로 검색어의 변화를 확인했습니다. 이후 실제 API를 연결하면서 로딩 여부와 API 검색 결과도 반응형 상태로 추가했습니다.

**진행하면서 느낀 점**

처음에는 `computed`, `watch`, `watchEffect`의 차이가 조금 헷갈렸습니다. 직접 검색 기능에 적용해보니 `computed`는 기존 데이터를 이용해 새로운 결과를 만들 때 사용되고 `watch`는 값이 바뀐 뒤 다른 작업을 처리할 때 사용한다는 차이를 더 잘 이해할 수 있었습니다.

### 3 - 화면을 컴포넌트로 나누기

처음에는 검색창과 날씨 카드가 한 파일에 모두 들어가 있었지만, 기능이 늘어나면서 역할에 따라 파일을 나눴습니다.

| 컴포넌트 | 역할 |
| --- | --- |
| `BaseDashboardCard.vue` | 검색·날씨·예보 영역에서 공통으로 사용하는 카드 틀 |
| `SearchBar.vue` | 검색어 입력과 검색 실행 |
| `WeatherCard.vue` | 도시별 날씨와 상세 정보 표시 |
| `UnitToggler.vue` | 섭씨·화씨 단위 변경 |
| `ForecastPanel.vue` | 5일 예보 목록 표시 |

데이터는 Props로 전달하고 클릭이나 검색 같은 사용자 동작은 Emits로 전달했습니다. 공통 카드에는 Slot을 넣어 같은 디자인 안에 검색창, 날씨 목록, 예보처럼 서로 다른 내용을 넣을 수 있게 했습니다.

**진행하면서 느낀 점**

처음에는 한 파일에 있던 코드를 여러 개로 나누는 게 오히려 더 복잡하게 느껴졌습니다. 그런데 검색창이나 날씨 카드처럼 역할별로 나눠보니 수정할 부분을 찾기가 더 편했고 한 파일에 코드가 몰려 있을 때보다 전체 구조도 잘 보였습니다.

### 4 - Vue Router로 페이지 만들기

메인 화면 외에도 상세 날씨, 서비스 소개, 생활 가이드, 404 화면을 각각 View로 만들었습니다. `/weather/:cityId` 경로에는 도시 ID를 전달해 해당 도시의 상세 정보를 보여주도록 했고, 존재하지 않는 주소는 404 페이지로 이동하도록 Catch-all Route를 설정했습니다.

날씨 카드를 클릭하면 현재 화면 안에서 상세 내용이 펼쳐지고, `상세 페이지` 버튼을 누르면 별도의 상세 주소로 이동합니다. 버튼을 눌렀을 때 카드 클릭까지 같이 발생하지 않도록 이벤트 버블링도 막았습니다.

**진행하면서 느낀 점**

처음에는 컴포넌트를 바꾸는 것과 페이지를 이동하는 것이 비슷하다고 생각했습니다. 상세 페이지 주소로 직접 들어가거나 새로고침해도 도시 ID에 맞는 내용이 나오는 것을 확인하면서 Router가 왜 필요한지 더 잘 알 수 있었습니다.

### 5 - Pinia로 온도 단위 공유하기

여러 화면에서 같은 온도 단위를 사용해야 해서 Pinia의 `configStore`를 만들었습니다. 현재 단위를 저장하는 `unit`, 단위 기호를 반환하는 `unitSymbol`, 섭씨와 화씨를 바꾸는 `toggleUnit`을 추가했습니다.

수업에서 요구한 내용에 더해 마지막 API 갱신 시각을 저장하는 `lastUpdated`, `formattedLastUpdated`, `markUpdated`도 추가했습니다. 단위를 바꾸면 메인 배너, 날씨 카드, 상세 페이지, 5일 예보가 모두 같이 바뀝니다.

**진행하면서 느낀 점**

처음에는 온도 단위를 각 컴포넌트에 따로 전달해야 한다고 생각했습니다. Pinia를 사용해보니 여러 화면에서 같이 쓰는 값은 Store에서 관리하는 게 훨씬 편했습니다. 그렇다고 모든 값을 Store에 넣기보다는 여러 곳에서 같이 사용하는 값만 넣는 것이 좋겠다고 느꼈습니다.

### 6 - Axios로 실제 날씨 API 연결하기

Axios를 이용해 OpenWeatherMap의 현재 날씨와 5일 예보 API를 연결했습니다. 도시명을 먼저 좌표로 변환한 뒤 같은 좌표를 현재 날씨와 예보 요청에 사용했습니다.

한글 도시명이 OpenWeatherMap에서 검색되지 않는 경우가 있어 Open-Meteo 지오코딩을 추가로 연결했고, 그래도 찾지 못할 때는 한글을 간단히 로마자로 바꿔 한 번 더 검색하도록 만들었습니다.

API 키는 코드에 직접 적지 않고 `VITE_OPENWEATHER_API_KEY` 환경 변수로 분리했습니다. API 요청에 실패하더라도 화면이 전부 비어버리지 않도록 기본 Mock Data는 그대로 남겨두고, 오류 내용은 상태 메시지로 보여주도록 했습니다.

**진행하면서 느낀 점**

Mock Data를 사용할 때는 정해진 값만 보여주면 됐지만 실제 API를 연결하니 검색 실패나 네트워크 오류도 같이 생각해야 했습니다. 특히 같은 도시도 한글과 영문 검색 결과가 달라질 수 있어서 생각보다 까다로웠습니다. 데이터를 잘 받아오는 것도 중요하지만 실패했을 때 화면이 멈추지 않게 처리하는 것도 중요하다고 느꼈습니다.

### 7 - Element Plus와 나만의 UI 적용하기

Element Plus를 전역으로 등록하고 새로고침 버튼과 온도 단위 버튼에 적용했습니다. 기본 예제 화면 그대로 두지 않고 보라색 사이드바, 대시보드 배너, 카드 펼침 효과, 날씨별 아이콘과 안내 문구를 추가했습니다.

개인 추가 화면으로 날씨별 생활 가이드를 만들었습니다. 맑은 날, 비 오는 날, 바람이 강한 날, 추운 날에 필요한 준비 사항을 확인할 수 있습니다. API 확장 기능으로는 서울의 5일 예보를 추가했습니다.

**진행하면서 느낀 점**

처음에는 UI Library를 사용하면 디자인을 거의 다 해결할 수 있을 거라고 생각했습니다. 직접 사용해보니 버튼처럼 자주 쓰는 요소는 편했지만 원하는 느낌을 만들려면 CSS도 같이 수정해야 했습니다. 라이브러리만 사용하는 것보다 필요한 부분에 골라서 쓰는 게 더 잘 맞았습니다.

### 8 - 코드 점검과 배포

ESLint로 오류를 확인하고 Prettier로 코드 형식을 정리했습니다. 스테이징과 프로덕션 환경을 구분할 수 있도록 Vite mode별 빌드 명령도 추가했습니다. API 키가 들어 있는 `.env.local`은 Git에 올라가지 않도록 제외했습니다.

마지막으로 `npm run lint`와 `npm run build`가 정상적으로 끝나는지 확인한 뒤 GitHub에 코드를 올리고 Vercel로 배포했습니다.

**진행하면서 느낀 점**

개발 서버에서 화면이 잘 보이면 끝난 줄 알았는데 실제로 배포하려면 환경 변수와 배포 경로도 따로 확인해야 했습니다. 중간에 생긴 오류를 린트와 빌드 과정에서 찾을 수 있었기 때문에 앞으로도 작업이 끝나면 두 명령을 먼저 실행해보려고 합니다.

## 프로젝트 구조

```text
src/
├── assets/                 # 전역 스타일과 이미지
├── components/
│   └── exercise/           # 최종 대시보드 컴포넌트
├── router/                 # 페이지 경로와 동적 라우트
├── services/               # 날씨·지오코딩 API 요청
├── stores/                 # Pinia 전역 설정
├── views/                  # 라우트 단위 화면
├── App.vue                 # 공통 사이드바와 RouterView
└── main.js                 # Vue, Router, Pinia, Element Plus 등록
```

## 실행 방법

### 1. 의존성 설치

```sh
npm install
```

### 2. 환경 변수 설정

`.env.example`을 참고해 프로젝트 루트에 `.env.local`을 만듭니다.

```env
VITE_OPENWEATHER_API_KEY=발급받은_API_KEY
```

API 키가 없어도 기본 Mock Data 화면은 확인할 수 있지만 실제 날씨 검색과 5일 예보는 사용할 수 없습니다.

### 3. 개발 서버 실행

```sh
npm run dev
```

### 4. 코드 점검 및 빌드

```sh
npm run lint
npm run build
npm run preview
```

## 환경별 빌드

```sh
npm run build:staging
npm run build:production
```

- `.env.staging`: 스테이징 환경 설정
- `.env.production`: 프로덕션 환경 설정
- `.env.local`: 개인 API 키이며 Git에 포함하지 않음

## 배포

- 배포 주소: [https://weatherly-skala.vercel.app](https://weatherly-skala.vercel.app)
- 배포 환경에는 `VITE_OPENWEATHER_API_KEY`를 별도로 등록해야 합니다.
- SPA의 동적 경로로 직접 접속해도 `index.html`로 연결되도록 Rewrite를 설정했습니다.

## 과제를 마치며

처음에는 날씨 데이터를 카드로 보여주는 간단한 화면이었는데 수업에서 배운 내용을 하나씩 추가하다 보니 검색부터 상세 페이지, 외부 API와 배포까지 연결된 서비스가 되었습니다.

과제를 진행하면서 기능을 하나 추가할 때 화면만 수정하면 되는 것이 아니라 데이터가 어디에서 관리되는지, 컴포넌트끼리 값을 어떻게 주고받는지, 오류가 나면 무엇을 보여줄지도 같이 생각해야 한다는 걸 알게 됐습니다. 매 단계의 예제를 따로 끝내지 않고 앞에서 만든 결과에 계속 기능을 추가해 마지막 배포까지 해본 점이 가장 기억에 남습니다.
